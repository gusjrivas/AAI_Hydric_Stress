## 2. Incidente reportado y su causa raíz CONFIRMADA (revisión: se retracta la hipótesis original)

En el primer lote de pruebas existentes (`f_batch2.log`) se incluyó por error, sin lectura previa completa, `backend/tests/test_replay.py`. Ese archivo usa `replay_packages/base-seed4-1157696b7b-v2` como fixture "real autorizada" según su propio docstring. Los 15 tests de ese archivo **fallaron con HTTP 503** ("El paquete autorizado no tiene predicciones" / "Paquete de reproducción histórica no disponible o inválido") — es decir, la ejecución **no expuso ni interpretó ningún valor de predicción/resultado real**; el paquete simplemente no cargó.

**Corrección respecto del informe anterior:** ese informe atribuía la 503 a una "hipótesis" no confirmada (incompatibilidad de versión pandas/pyarrow). Esa hipótesis **se descarta explícitamente** — se investigó la causa exacta con un diagnóstico puntual y acotado (permitido: llamar a la misma función de carga que usa la dependencia de FastAPI, capturando únicamente tipo/mensaje de excepción — el mismo texto que el propio backend expondría en el `detail` de un 503 real — sin leer ni imprimir ningún valor de fila de `predictions.json`). Script: `fixtures/f06f07_diagnose_503.py`; log: `logs/f06f07_diagnose_503.log`.

**Causa raíz confirmada:** `historical_replay.package_loader.load_package` lanza `IntegrityError: Hash de custodia no coincide para 'effective_configuration.json': esperado 4834955f..., obtenido c493ea49...` desde `_verify_file_integrity` (`package_loader.py:118`). Se verificó exactamente por qué:

- `git show HEAD:replay_packages/base-seed4-1157696b7b-v2/effective_configuration.json | sha256sum` → `4834955f440cde80b79101b394bfeb55429232a476515c16297d21eacb1c75fe` — coincide EXACTAMENTE con el `custody_sha256` declarado en `manifest.json`.
- El archivo tal como está en el **working tree** del worktree de auditoría hashea a `c493ea4950ce5632c66dc6531d5c74a7334522abfc16fffdd462fb6f2fc37eec` — **no coincide**.
- `git config --get core.autocrlf` → `true`. Este es exactamente el mecanismo: la configuración de Git de esta máquina convierte finales de línea LF→CRLF al hacer checkout de archivos de texto, lo que altera los bytes de cualquier archivo JSON del paquete respecto del blob committeado, y por lo tanto su SHA-256. Se verificó el mismo patrón, no solo para `effective_configuration.json`, sino también para `predictions.json` y `run_metadata.json` (los 3 archivos de texto listados en `manifest["files"]`): sus hashes de working tree difieren de los `custody_sha256` declarados, mientras que los 2 archivos binarios (`dataset/*.parquet`, `derived/*.parquet`, no afectados por conversión de fin de línea) sí coinciden. `_verify_file_integrity` itera el diccionario del manifiesto y aborta en el primer mismatch que encuentra (`effective_configuration.json`), por eso ese fue el único mensaje observado en el log de pytest, pero el problema es sistémico a los 3 archivos de texto del paquete en este checkout.
- Esto es coherente con un antecedente ya conocido por el propio proyecto: el commit `90183d3` ("fix(historical-replay): make imputation source-drift hash checkout-independent") corrigió exactamente esta misma clase de problema (hash dependiente de checkout CRLF/LF en Windows con `core.autocrlf=true`) para otro archivo (`src/data_quality/imputation.py`/`temporal.py`, verificado contra `verify_imputation_source_matches_verified_commit`). La corrección análoga **no se aplicó** al mecanismo de `custody_sha256` de `_verify_file_integrity` en `package_loader.py`, que sigue siendo sensible a la configuración de checkout del sistema operativo/Git en el que se ejecuta.

**Conclusión:** esto **no es** un defecto de código específico de esta auditoría, **no es** una incompatibilidad de versión de pandas/pyarrow (esa hipótesis queda descartada por evidencia directa), y **no es** un problema del contenido real del paquete (el blob committeado en git es correcto y coincide con el manifiesto). Es un artefacto de la configuración de checkout (`core.autocrlf=true`) de esta máquina de auditoría, de la misma naturaleza que un bug ya corregido una vez en este mismo repositorio para otro archivo. Es plausible que el mismo problema ocurra en cualquier checkout de Windows con `core.autocrlf=true` que no haya sido normalizado, lo cual señala una fragilidad real del mecanismo de custodia de hashes de `package_loader.py` (no normaliza finales de línea antes de hashear archivos de texto, a diferencia de la corrección ya aplicada en `imputation_markers.py`) — se documenta como observación relevante, pero **no se agrega como hallazgo F-xx nuevo ni se propone su corrección en el encargo**, porque excede el mandato original de esta auditoría (los IDs F-01..F-12 no cubren `package_loader.py::_verify_file_integrity` como tal) y porque corregirlo requeriría decidir si el criterio de custodia debe normalizar line-endings (lo cual es una decisión de diseño sobre la garantía de integridad, no una corrección mecánica trivial).

**Qué acceso puntual haría falta para revalidar el contrato HTTP completo contra el paquete real:** normalizar los archivos de texto de `replay_packages/base-seed4-1157696b7b-v2/` a LF en el working tree (p. ej. re-checkout con `core.autocrlf=input`/`false`) antes de levantar el servidor de pruebas. Esto modificaría archivos bajo `replay_packages/`, lo cual está fuera del alcance de solo-lectura autorizado para esta auditoría — se señala como el acceso puntual necesario, sin ejecutarlo. Alternativamente, ejecutar la misma suite en un entorno Linux/CI con checkout LF nativo evitaría el problema sin tocar el worktree de auditoría.

**Tratamiento formal:** esto se registra como **BLOCKED** (no como "PASS con alcance HTTP bloqueado") para toda evidencia HTTP end-to-end sobre F-06/F-07/D-06 que dependía de `backend/tests/test_replay.py` contra el paquete real. Las comprobaciones de F-07 alcanzadas con fixtures sintéticas propias y con `tests/test_historical_replay_projection.py`/`test_historical_replay_feedback.py` (que NO pasan por `_verify_file_integrity` del paquete real y sí ejecutaron y pasaron) se reportan como resultado **parcial**, separado explícitamente del resultado BLOCKED. El checkout original (`C:/Repo/AAI_Hydric_Stress`) y sus 8 modificaciones ajenas bajo `replay_packages/` no fueron tocados por este incidente (no se escribió nada; solo lecturas y una llamada a una función Python en memoria, sin servidor HTTP en esta repetición del diagnóstico).

### F-08 — Concurrencia del feedback de replay — **FAIL (hallazgo confirmado, reproducible, re-verificado con rigor adicional)**

- Código: `src/historical_replay/feedback.py::ReplayFeedbackStore.append` — abre el archivo en modo `"a"` (append de texto) sin ningún lock.

**Verificación rigurosa de la fixture (revisión solicitada):**
- Se construyó `fixtures/f08_replay_feedback_concurrency_v2.py`, que además de repetir el experimento (8 procesos × 200 registros, `multiprocessing.Barrier` para forzar arranque simultáneo) agrega: captura de `exit_code` de cada proceso hijo, redirección de stdout/stderr de cada worker a un archivo propio revisado después del `join`, y conteo de bytes esperados vs. bytes reales en disco.
- **Exit codes:** los 8 procesos terminaron con `exitcode=0` (`all_exitcodes_zero=True`). Ningún proceso lanzó excepción (`any_worker_exception=False`; se revisaron los 8 logs individuales).
- **Método real bajo prueba:** cada worker importa `ReplayFeedbackStore`/`ReplayFeedbackRecord` desde `historical_replay.feedback` y llama `store.append(rec)` — el método real auditado, no una reimplementación.
- **Orden de conteo:** el conteo de líneas se realiza después de `for p in procs: p.join()` (los 8 `join()` completan antes de abrir y leer el archivo) — no hay lectura concurrente con escritura activa.
- **Resultado de esta repetición:** `total_expected_bytes=493520` (calculado independientemente por cada worker, sumando el tamaño exacto de cada línea que efectivamente pasó a `store.append`) vs. `actual_file_size_bytes=374447` → **119073 bytes ausentes en disco** (24 % del contenido esperado). `expected_lines=1600 actual_lines=1210` (**390 líneas completas perdidas**), `unparseable_lines=0` en esta repetición particular. Log: `logs/f08_replay_feedback_concurrency_v2.log`.
- La primera corrida (`f08_replay_feedback_concurrency.log`, sin las verificaciones de exit code añadidas después) había mostrado 411 líneas perdidas y 1 línea corrupta — la variabilidad entre corridas (líneas perdidas puras vs. una línea corrupta ocasional) es consistente con una condición de carrera no determinista, no con un bug determinístico de una sola forma.

**Aislamiento del mecanismo (experimento adicional, revisión solicitada):** se construyó `fixtures/f08_mechanism_isolation.py`, que compara, bajo el mismo patrón de concurrencia, (A) `open(path, "a", encoding="utf-8")` de Python (lo que hace `ReplayFeedbackStore.append` hoy) contra (B) `os.open(path, os.O_WRONLY | os.O_CREAT | os.O_APPEND)` + `os.write()` a nivel de sistema operativo, con apertura/escritura/cierre por registro en ambos casos. **Resultado:** ambas variantes pierden datos de forma comparable — (A) perdió 307/1600 líneas, (B) perdió 332/1600 líneas y además produjo 2 líneas no parseables (log: `logs/f08_mechanism_isolation.log`). **Conclusión sobre el mecanismo, con la evidencia que efectivamente se tiene:** la pérdida **no es específica de la capa de buffering de `io` en modo texto de Python** (se reproduce igual con un `os.open`/`os.write` de bajo nivel con `O_APPEND` explícito). Esto es consistente con que, en Windows, el flag `O_APPEND` (vía la capa de runtime de C) no garantiza la misma atomicidad "seek-y-escritura-atómica-entre-procesos" que sí ofrece POSIX/Linux para escrituras pequeñas. **No se inspeccionaron directamente los flags de apertura a nivel Win32/NT (`FILE_APPEND_DATA` vs. `GENERIC_WRITE`+`SetFilePointer`)** con una herramienta como Process Monitor o el propio código fuente del runtime de Windows — esta conclusión se apoya en el comportamiento comparado de ambas variantes, no en inspección directa del kernel/handle. Se deja explícito: **causa exacta a nivel de API del sistema operativo no aislada con inspección directa de flags; solo se confirma el efecto (pérdida de datos) y se descarta que el efecto sea atribuible únicamente a la elección de API de E/S de Python** (ambas pierden datos de forma comparable).

**Entorno de la repetición:** `platform.platform() = Windows-11-10.0.26200-SP0`, Python `3.13.14` (`C:\tcnenv\Scripts\python.exe`), directorio temporal en unidad `C:\` con sistema de archivos **NTFS** (confirmado con `GetVolumeInformationW`). Tamaño de cada registro JSONL: ~308-309 bytes (línea completa, incluye el padding `"X"*50` del fixture).

**Separación explícita pedida:**
- **Defecto reproducido (confirmado):** pérdida silenciosa de bytes/líneas de feedback bajo escritura concurrente real de múltiples procesos al mismo archivo, en este entorno Windows/NTFS, independientemente de si se usa la API de alto nivel de Python o `os.open`/`os.write` de bajo nivel con `O_APPEND`. Esto **sí** está confirmado con evidencia reproducible.
- **Incumplimiento de un contrato de uso declarado:** **NO** — no se encontró ninguna fuente vigente (spec, ADR, documento de cierre) que declare o exija concurrencia multi-escritor para `ReplayFeedbackStore`. La demo de replay está documentada como recorrido de un solo usuario/sesión (ver D-04). Por lo tanto esto **no es un incumplimiento contractual**; es una **limitación no documentada** de un mecanismo que, si el modelo de uso llegara a admitir dos sesiones concurrentes sobre el mismo `package_id` (plausible con revisores concurrentes en una demo), produciría pérdida silenciosa de evidencia de feedback sin ninguna excepción visible al cliente. Severidad: media, condicionada a ese escenario de uso.
- Contraste con F-04: `operational_repository.py` sí usa un lock interproceso real (`msvcrt.locking`/`fcntl.flock`) para su ciclo lectura-modificación-escritura; `ReplayFeedbackStore.append` no tiene ningún mecanismo equivalente.
